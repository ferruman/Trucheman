# PRD: Book Translator

**Версия:** 1.0 (local-first MVP)  
**Статус:** готов к реализации  
**Основной пользователь:** владелец локальной установки

## 1. Краткое описание

Book Translator — локальное веб-приложение для двухпроходного перевода EPUB-книг через внешний LLM API. Первый проход создаёт полный черновой перевод, второй редактирует его по оригиналу: исправляет смысловые ошибки, язык и стиль, одновременно проверяя согласованность имён. Приложение сохраняет структуру, разметку, изображения и служебные файлы книги, заранее извлекает словарь имён, показывает ход работы и продолжает незавершённую задачу после перезапуска.

Приложение запускается на компьютере пользователя и открывается в браузере. В MVP нет аккаунтов, облачного сервера, совместной работы и публикации в интернете.

Главный результат MVP: пользователь выбирает EPUB, проверяет предложенный словарь имён, запускает перевод с обязательной редактурой и получает пригодный для чтения валидный EPUB.

**North star:** EPUB на выбранном исходном языке → EPUB на выбранном целевом языке, который можно сразу открыть в обычной читалке и читать как законченную книгу. Основной контрольный сценарий — English → Russian; дополнительный — German → Polish.

## 2. Контекст и продуктовые принципы

Это персональный инструмент, поэтому приоритеты такие:

1. Надёжно закончить длинный перевод, даже если процесс или API временно упали.
2. Не повредить EPUB и не потерять уже готовые части.
3. Дать пользователю контроль над терминами и переводческими инструкциями.
4. Сделать установку и запуск простыми на одном компьютере.
5. Считать результатом только прошедший переводческий и редакторский проходы текст; стоимость оптимизировать без отказа от обязательной редактуры.

Local-first не означает полностью offline: файлы и состояние хранятся локально, но текст книги отправляется выбранному LLM-провайдеру. Интерфейс должен явно предупреждать об этом.

## 3. Цели MVP

- Импортировать EPUB 2/3 без DRM.
- Позволить выбрать исходный и целевой языки; архитектура не должна быть привязана только к английскому и русскому.
- Определить порядок чтения по package document и spine, а не по именам файлов.
- Переводить пользовательский текст, не передавая модели ответственность за HTML/XML-разметку.
- Сохранять структуру книги, изображения, CSS, ссылки, сноски и прочие нетекстовые ресурсы.
- Автоматически предложить словарь имён и дать проверить или исправить его до перевода.
- Поддерживать общие инструкции переводчику и редактору.
- Выполнять отдельный редакторский проход по оригиналу и черновому переводу.
- Показывать прогресс по главам и фрагментам, текущую операцию и ошибки.
- Поддерживать паузу, продолжение и восстановление после перезапуска приложения.
- Позволять повторить неудавшийся фрагмент или главу.
- Собрать и скачать итоговый EPUB.
- Проверить итоговый файл до выдачи пользователю.

## 4. Не входит в MVP

- Аккаунты, роли, синхронизация и облачное хранение.
- Публичный деплой, Docker/Kubernetes и удалённая очередь задач.
- Совместное редактирование.
- Форматы PDF, DOCX, MOBI и AZW.
- EPUB с DRM.
- Собственные модели и локальный inference.
- Платежи и автоматический биллинг.
- Полноценный CAT-интерфейс и визуальный редактор всей книги.
- Автоматическая атрибуция реплик и профили голосов персонажей.
- Одновременный перевод нескольких книг.

Профили персонажей можно добавить после проверки базового пайплайна. В MVP их пользу частично покрывает свободное поле «Инструкции переводчику и редактору».

## 5. Основной пользовательский сценарий

### 5.1 Первый запуск

1. Пользователь запускает приложение одной командой.
2. Приложение открывает или показывает адрес локального интерфейса, например `http://127.0.0.1:3000`.
3. Пользователь указывает параметры LLM-провайдера: endpoint, имя модели и API-ключ.
4. Приложение выполняет короткую проверку соединения. Ключ хранится отдельно от job-файлов и никогда не попадает в экспорт или лог.

### 5.2 Новый перевод

1. Пользователь выбирает EPUB.
2. Приложение создаёт локальную задачу, проверяет архив и предлагает исходный язык; пользователь выбирает целевой язык.
3. Приложение анализирует текст и извлекает имена персонажей, мест и другие собственные имена вместе с предлагаемым переводом.
4. Пользователь просматривает таблицу имён, исправляет варианты, отключает лишние строки или добавляет недостающие.
5. При необходимости пользователь задаёт общие инструкции о стиле и особенностях книги.
6. Пользователь нажимает «Начать перевод».
7. Пайплайн последовательно выполняет для каждого фрагмента черновой перевод и редактуру по оригиналу. Отредактированный вариант считается финальным.
8. Экран задачи показывает общую готовность, текущую фазу (`перевод` или `редактура`), главу, последние события и кнопки «Остановить» / «Продолжить».
9. «Остановить» означает безопасную паузу: новые LLM-запросы не запускаются, текущий запрос завершается, а его проверенный результат и состояние сохраняются.
10. Ошибка отдельного фрагмента автоматически повторяется с ограниченной задержкой. После исчерпания попыток задача переходит в состояние `needs_attention`, не теряя черновые и отредактированные результаты.
11. После обработки приложение выполняет итоговые проверки и собирает EPUB.
12. Пользователь скачивает итоговый файл.

### 5.3 Возврат после перезапуска

На главной странице виден список локальных задач. Закрытие только браузерной вкладки не прерывает работающий backend; при повторном открытии UI подключается к текущей задаче. Кнопка «Остановить» или завершение Node.js-процесса оставляют задачу в `paused` или `needs_attention`, а не в ложном `running`. Пользователь нажимает «Продолжить», и работа начинается с первого незавершённого переводческого или редакторского шага без повторной оплаты готовых шагов.

## 6. Интерфейс MVP

### Экран «Задачи»

- Кнопка «Новый перевод».
- Список задач: название книги, языковая пара, дата, текущая фаза, прогресс.
- Действия: открыть, продолжить, удалить с подтверждением.
- Ссылка на локальные настройки.

### Шаг 1 — «Выбрать книгу»

- Выбор EPUB через системный file picker.
- Исходный язык с автоопределением и возможностью исправить; значение по умолчанию — English (`en`).
- Целевой язык выбирается явно; значение по умолчанию — Russian (`ru`), исходный и целевой языки не могут совпадать.
- В первой версии список как минимум включает English, Russian, German и Polish и хранит значения как BCP 47 language tags (`en`, `ru`, `de`, `pl`). Добавление языка в список не должно требовать изменений переводческого пайплайна.
- После выбора сразу запускаются проверка EPUB и извлечение словаря имён.
- Пока идёт анализ, UI показывает понятный статус и лог; перевод ещё не запускается.

### Шаг 2 — «Проверить имена»

- Таблица `оригинал | предлагаемый перевод | тип | использовать`.
- Добавление, удаление и inline-редактирование строк.
- Категории: персонаж, место, организация, другое собственное имя.
- Большое необязательное поле «Инструкции переводчику и редактору».
- Кнопка «Начать перевод» доступна после завершения анализа; пользователь не обязан менять предложенные значения.

### Экран «Ход перевода»

- Один общий прогресс всего двухпроходного пайплайна и прогресс текущей главы.
- Счётчики `переведено / отредактировано / всего / с ошибкой`.
- Текущий этап: подготовка, извлечение имён, перевод, редактура, проверка, сборка.
- Список глав со статусами.
- Компактный журнал событий без полного текста книги и без секретов.
- Основная кнопка «Остановить» во время работы и «Продолжить» после безопасной паузы.
- Кнопка «Повторить ошибку», если задача требует вмешательства.
- Закрытие браузерной вкладки не останавливает backend; для остановки используется кнопка. Завершение backend-процесса также не теряет checkpoint.

### Экран «Результат»

- Результат валидации и список предупреждений с привязкой к главе.
- Краткая статистика: переведённые и отредактированные фрагменты, повторные запросы, примерное использование токенов, время.
- Действия: повторить главу, пересобрать EPUB, скачать EPUB.

Интерфейс рассчитан на desktop. Мобильная адаптация достаточна на уровне читаемости, но не является критерием MVP.

## 7. Функциональные требования

### FR-1. Импорт и безопасность EPUB

- Принимать только файл с расширением `.epub`, но проверять содержимое, а не доверять расширению.
- Ограничения размера и распакованного объёма задаются конфигурацией.
- Защищаться от path traversal/ZIP Slip и zip bomb.
- Не изменять исходный файл; работать с копией внутри каталога задачи.
- Показывать понятную ошибку для DRM, битого ZIP или отсутствующего package document.

### FR-2. Разбор структуры

- Найти package document через `META-INF/container.xml`.
- Прочитать manifest, spine и свойства ресурсов.
- Переводить только подходящие XHTML/HTML-документы из reading order.
- Не переводить CSS, JavaScript, SVG path data, бинарные ресурсы, URL и служебные идентификаторы.
- Отдельно решить судьбу navigation document, TOC и metadata: в MVP допускается сохранять их исходный текст, но книга должна оставаться навигируемой.

### FR-3. Подготовка переводимого текста

- Парсить документ в DOM.
- Извлекать только видимые текстовые узлы из разрешённых элементов.
- Исключать `script`, `style`, `code`, `pre`, `math` и элементы, явно помеченные как непереводимые.
- Каждому текстовому сегменту присваивать стабильный локальный ID.
- Сохранять пробелы до/после текста, типографику и связь сегмента с исходным DOM.
- Не отправлять модели целую HTML-страницу с просьбой «не менять теги».

### FR-4. Батчинг

- Группировать соседние сегменты в пределах одного документа.
- Ограничение задавать в токенах модели, если доступен tokenizer, иначе использовать консервативную оценку по символам.
- Никогда не смешивать сегменты разных документов в одном запросе.
- Слишком длинный сегмент делить сначала по абзацам/фразам, затем по предложениям через `Intl.Segmenter` с учётом исходного языка.
- Размер батча и резерв на ответ должны настраиваться для модели; фиксированное значение `24 000 символов` не является универсальным.

### FR-5. Контракт с LLM

Модель получает структурированный список:

```json
{
  "segments": [
    { "id": "s-001", "text": "Original text" },
    { "id": "s-002", "text": "Next paragraph" }
  ]
}
```

Ожидаемый ответ содержит те же ID и только переводимый текст:

```json
{
  "segments": [
    { "id": "s-001", "text": "Переведённый текст" },
    { "id": "s-002", "text": "Следующий абзац" }
  ]
}
```

Системная инструкция включает языковую пару, пользовательские инструкции, подтверждённый словарь имён и небольшой контекст. Контекст не заменяет сегменты ответа и не вставляется в результат.

Промпт получает и человекочитаемые названия языков, и их BCP 47 tags. Проверки языка не должны предполагать конкретную письменность или фиксированное соотношение длины English → Russian.

Первый адаптер MVP — DeepSeek через OpenAI-compatible Chat Completions API. Имя модели задаётся конфигурацией и не зашивается в пайплайн. Используется JSON mode, но API может вернуть пустой или обрезанный ответ, поэтому schema validation и retry всё равно обязательны.

OpenAI добавляется вторым провайдерским профилем после стабилизации пайплайна. Внутренний интерфейс провайдера должен скрывать различия API, чтобы переводчик и редактор не зависели от конкретного SDK. Другие протоколы, включая нативный Anthropic API, требуют отдельных адаптеров и не считаются автоматически совместимыми.

### FR-6. Обязательная редактура

- Для каждой главы сначала завершить черновой перевод всех её батчей, затем запустить редакторский проход.
- Редактор получает для каждого батча оригинальные сегменты, черновой перевод с теми же ID, подтверждённый словарь имён, пользовательские инструкции и read-only контекст соседних сегментов.
- Задача редактора: исправить смысловые и фактические искажения относительно оригинала, грамматику, лексику, пунктуацию, неестественные кальки, стиль и несоблюдение словаря.
- Редактор не должен сокращать, пересказывать, цензурировать или добавлять содержание без прямой пользовательской инструкции.
- Ответ редактора использует тот же ID-контракт. В финальный EPUB попадает только проверенный редакторский результат.
- Черновой перевод и отредактированный результат сохраняются раздельно. Это позволяет повторить только редактуру, не оплачивая перевод заново.
- Если редактура фрагмента не завершена, черновик не считается готовым результатом и не попадает в обычную финальную сборку.
- По умолчанию перевод и редактура используют DeepSeek. Для каждого прохода хранится отдельный профиль модели, поэтому позднее редактуру или оба прохода можно переключить на OpenAI и сравнить качество.

### FR-7. Проверка ответа

Жёсткие проверки, при которых запрос повторяется:

- ответ соответствует ожидаемой JSON-схеме;
- присутствуют все и только ожидаемые ID;
- каждый непустой исходный сегмент имеет непустой результат;
- результат можно безопасно вставить как текст в исходный DOM;
- провайдер не вернул отказ, обрыв ответа или служебное сообщение вместо перевода.

Мягкие проверки, создающие предупреждение:

- подозрительно короткий или длинный результат;
- большая доля текста осталась на исходном языке;
- подтверждённый вариант имени не соблюдён;
- появились повторяющиеся фразы или типичные вводные сообщения модели.

Количество предложений до и после перевода не должно быть жёстким критерием: корректный перевод вправе объединять или разделять предложения.

Жёсткие проверки применяются отдельно к черновому переводу и редакторскому ответу. Дополнительно финальная редактура проверяется против оригинала, чтобы модель не потеряла сегменты и не превратила перевод в пересказ.

### FR-8. Повторы и управление скоростью

- Повторять временные ошибки (`429`, `5xx`, timeout) с exponential backoff и jitter.
- Учитывать `Retry-After`, если он есть.
- Не повторять бесконечно ошибки конфигурации (`401`, неизвестная модель, неверный endpoint).
- По умолчанию обрабатывать один LLM-запрос одновременно. Параллельность можно увеличить в настройках позднее.
- После заданного числа попыток помечать фрагмент как `failed`, а задачу — `needs_attention`.
- Пауза прекращает выдачу новых запросов; уже начатый запрос можно дождаться и атомарно сохранить.

### FR-9. Восстановление

- Сохранять черновой и отредактированный результат каждого успешно проверенного батча сразу и независимо.
- Записывать состояние атомарно через временный файл и rename.
- При старте находить задачи, оставшиеся в `running`, и переводить их в `paused`.
- Продолжение не должно повторно оплачивать уже успешно завершённый перевод или редактуру батча.
- Изменение словаря имён после старта не меняет готовые батчи автоматически. UI должен предложить продолжить только для новых батчей либо явно повторить выбранные главы.

### FR-10. Сборка EPUB

- Вставлять отредактированные переводы в копию DOM как текст, сохраняя элементы и атрибуты.
- Сохранять относительные пути и все нетронутые ресурсы.
- При упаковке соблюдать требования EPUB ZIP, включая корректное размещение и способ сжатия `mimetype`.
- Изменить язык книги на целевой; заголовок и имя автора в MVP можно оставить без перевода.
- Не перезаписывать ранее собранный файл до успешного окончания новой сборки.

### FR-11. Итоговая валидация

- Архив открывается и содержит обязательные файлы.
- Package document, manifest и spine разрешаются без потерянных ресурсов.
- Все XHTML/XML-файлы, изменённые приложением, остаются корректно парсящимися.
- Число документов в spine совпадает с исходным.
- В итоговом архиве нет абсолютных локальных путей и файлов состояния приложения.
- Если доступен локальный EPUBCheck, запускать его как дополнительную проверку; его отсутствие не блокирует MVP.

## 8. Автоматический словарь имён

Извлечение словаря имён — обязательный шаг между импортом EPUB и запуском перевода. Пользователь всегда видит предложения модели и может принять их без изменений, исправить или дополнить.

### Вход

- Текст всех глав порциями, чтобы не пропустить персонажа, появляющегося поздно; повторяющиеся формы дедуплицируются после каждого батча.
- Исходный и целевой языки.

### Результат

```json
[
  {
    "source": "Stephen Dedalus",
    "target": "Стивен Дедал",
    "category": "character",
    "note": "",
    "enabled": true
  }
]
```

### Правила

- Извлекаются имена и прозвища персонажей, географические названия, организации и другие собственные имена.
- Дедупликация без учёта регистра с сохранением канонической формы; варианты имени можно связать с одной сущностью.
- Пользователь подтверждает и редактирует предложения до старта.
- Поддерживаются категории `character`, `place`, `organization`, `other`.
- При большом словаре в каждый запрос передаются глобальные обязательные и релевантные текущему батчу имена.
- Результат анализа кэшируется в задаче и может быть перезапущен вручную.
- Если извлечение остановлено, уже найденные имена сохраняются; после возобновления анализ продолжается с первого необработанного батча.
- Словарь имён принадлежит конкретной языковой паре. Смена целевого языка очищает предложенные переводы имён и все результаты перевода/редактуры после явного подтверждения пользователя.

Автоматический стилевой анализ и голоса персонажей не нужны для первого сквозного релиза. Качество обеспечивает обязательный редакторский проход, а дополнительные правила пользователь может сформулировать в поле инструкций. После MVP стилевой анализ можно добавить как генератор черновика этих инструкций.

## 9. Техническая архитектура

### 9.1 Общая схема

```text
Browser (React)
    │ HTTP + SSE
    ▼
Local Node.js server
    ├── REST API and static frontend
    ├── one in-process job runner
    ├── EPUB parse / transform / build
    ├── LLM provider adapter
    └── local filesystem storage
```

Один процесс Node.js обслуживает UI и выполняет одну активную задачу. Отдельный worker, Redis и внешняя база данных для MVP не нужны.

### 9.2 Рекомендуемый стек

| Область | Выбор | Причина |
|---|---|---|
| Язык | TypeScript | Общие типы API, job state и LLM-схем |
| Backend | Node.js + Express | Простой локальный HTTP/SSE-сервер |
| Frontend | React + Vite | Удобное управление пошаговым сценарием и таблицей имён |
| Валидация данных | Zod | Проверка API, конфигурации и ответа LLM |
| ZIP | отдельная ZIP-библиотека | Нужен полный контроль распаковки и EPUB-упаковки |
| XML/HTML | XML/DOM-парсер | Корректная работа с XHTML и namespaces |
| IDs | `crypto.randomUUID()` | Не требует отдельной зависимости |
| Тесты | Vitest | Unit и integration tests в одном стеке |

Конкретные ZIP/XML-библиотеки выбираются коротким техническим spike: они должны сохранять бинарные файлы, пути и XML без нежелательной нормализации. Не следует предполагать, что библиотека с названием `epub` умеет без потерь пересобирать произвольный EPUB.

### 9.3 Режимы запуска

- Development: Vite dev server и Node.js server отдельными процессами.
- Local production: Node.js раздаёт собранный frontend и API с одного origin.
- Сервер по умолчанию слушает только `127.0.0.1`.
- CORS в local production не нужен.

## 10. Локальное хранение

```text
data/
├── settings.json                 # без API-ключей
├── secrets.env                   # локально, gitignored, права доступа ограничены
└── jobs/
    └── <job-id>/
        ├── job.json
        ├── source.epub
        ├── source/               # безопасно распакованная рабочая копия
        ├── segments/
        │   ├── manifest.json
        │   ├── drafts.ndjson      # результат переводческого прохода
        │   └── edited.ndjson      # финальный редакторский результат
        ├── logs/
        │   └── events.ndjson
        ├── output/
        │   └── translated.epub
        └── tmp/
```

`data/` целиком исключается из Git. Полный оригинальный/переведённый текст не пишется в обычный журнал событий.

### Минимальное состояние задачи

```json
{
  "schemaVersion": 1,
  "id": "uuid",
  "status": "draft",
  "createdAt": "ISO timestamp",
  "updatedAt": "ISO timestamp",
  "source": {
    "filename": "book.epub",
    "language": "en",
    "fingerprint": "sha256"
  },
  "targetLanguage": "ru",
  "instructions": "",
  "nameGlossary": [],
  "currentStage": "name_analysis",
  "documents": [
    {
      "id": "doc-001",
      "href": "Text/chapter1.xhtml",
      "title": "Chapter 1",
      "status": "pending",
      "totalBatches": 8,
      "translatedBatches": 0,
      "editedBatches": 0
    }
  ],
  "progress": {
    "totalBatches": 47,
    "translatedBatches": 0,
    "editedBatches": 0,
    "completedSteps": 0,
    "totalSteps": 94,
    "failedBatches": 0
  },
  "lastError": null,
  "outputPath": null
}
```

Допустимые статусы задачи:

```text
draft → preparing → analyzing_names → awaiting_name_review → running
                                                              │
                                      running → stopping → paused → running
                                                              │
                                      running → needs_attention → running
                                                              │
                                      running → validating → completed
                                                              │
                                      running ───────────────→ failed
```

Во время `running` поле `currentStage` принимает значения `translation`, `editing` или `building`. Общий процент во время обработки считается как `(translatedBatches + editedBatches) / (2 × totalBatches)`, поэтому перевод без редактуры показывает не более 50% готовности.

Удаление задачи — единственная операция, которая удаляет исходник и промежуточные результаты; она всегда требует подтверждения.

## 11. Локальный API

Минимальный контракт:

| Метод | Path | Назначение |
|---|---|---|
| `GET` | `/api/health` | Состояние локального сервера |
| `GET` | `/api/settings` | Несекретные настройки и факт наличия ключа |
| `PUT` | `/api/settings` | Обновить настройки |
| `POST` | `/api/settings/test` | Проверить LLM-провайдера |
| `GET` | `/api/jobs` | Список задач |
| `POST` | `/api/jobs` | Загрузить EPUB и создать задачу |
| `GET` | `/api/jobs/:id` | Состояние задачи |
| `PUT` | `/api/jobs/:id/config` | Языки, инструкции, словарь имён |
| `POST` | `/api/jobs/:id/names/analyze` | Запустить или повторить извлечение имён |
| `POST` | `/api/jobs/:id/start` | Запустить/продолжить |
| `POST` | `/api/jobs/:id/pause` | Безопасно остановить и поставить на паузу |
| `POST` | `/api/jobs/:id/retry` | Повторить failed batch или главу |
| `POST` | `/api/jobs/:id/build` | Пересобрать результат |
| `GET` | `/api/jobs/:id/events` | SSE-события |
| `GET` | `/api/jobs/:id/download` | Скачать итоговый EPUB |
| `DELETE` | `/api/jobs/:id` | Удалить локальную задачу |

SSE используется только для удобного обновления UI. Источник истины — сохранённое состояние, поэтому после разрыва соединения клиент запрашивает `GET /api/jobs/:id` и переподключается. События должны иметь `id`, чтобы поддержать `Last-Event-ID`.

Пример события:

```json
{
  "id": 104,
  "type": "batch.completed",
  "timestamp": "2026-08-08T10:15:00.000Z",
  "jobId": "uuid",
  "documentId": "doc-003",
  "completed": 23,
  "total": 47,
  "stage": "editing",
  "message": "Глава 3: редактура фрагмента 2 из 8 готова"
}
```

## 12. Конфигурация модели

Вместо жёсткой привязки к названию текущей модели приложение хранит два профиля: для перевода и для редактуры. Изначально оба используют DeepSeek, но настраиваются независимо:

```json
{
  "profiles": {
    "translation": {
      "provider": "deepseek",
      "baseURL": "https://api.deepseek.com",
      "model": "configured-deepseek-model"
    },
    "editing": {
      "provider": "deepseek",
      "baseURL": "https://api.deepseek.com",
      "model": "configured-deepseek-model"
    }
  },
  "limits": {
    "contextTokens": 64000,
    "maxOutputTokens": 8000,
    "requestsPerMinute": 20
  }
}
```

API-ключ DeepSeek поступает из `DEEPSEEK_API_KEY`, будущий ключ OpenAI — из `OPENAI_API_KEY`, либо из системного secret store. UI возвращает только `hasApiKey: true/false` для каждого профиля.

Первая реализация использует обычный Chat Completions и JSON mode DeepSeek. Имя актуальной модели выбирается в настройках: псевдонимы и возможности моделей меняются независимо от приложения. OpenAI подключается отдельным адаптером после стабилизации DeepSeek-пайплайна; существующая задача запоминает провайдера и модель каждого уже выполненного шага.

Цены моделей не зашиваются в PRD или код как константа. Пользователь при желании задаёт input/output price в настройках, после чего приложение показывает приблизительную стоимость по фактическому usage из ответов провайдера.

## 13. Нефункциональные требования

### Надёжность

- Завершённый батч переживает аварийное завершение процесса.
- Повторный запуск идемпотентен для уже готовых батчей.
- Исходный EPUB остаётся неизменным.
- Запись состояния и финального файла атомарна.

### Безопасность и приватность

- Сервер слушает loopback-интерфейс по умолчанию.
- API-ключ не попадает в frontend bundle, job state, события и логи.
- Пользователь видит уведомление, что текст отправляется внешнему провайдеру.
- Имена файлов нормализуются, пути из архива проверяются.
- В логах ошибки провайдера очищаются от потенциальных секретов и полного prompt body.

### Производительность

- UI остаётся отзывчивым во время перевода.
- Большой EPUB обрабатывается потоково или по документам, без необходимости держать распакованную книгу и все переводы в памяти одновременно.
- Список задач и открытие существующей задачи не зависят от доступности LLM API.

### Совместимость

- Основной таргет — актуальный desktop-браузер на машине пользователя.
- Пути и операции с файлами должны работать на macOS, Windows и Linux; первый реально протестированный таргет можно ограничить ОС пользователя.

## 14. Критерии приёмки MVP

1. На тестовом EPUB с текстом, CSS, изображением, внутренней ссылкой и сноской приложение создаёт двухпроходный перевод и валидный открываемый EPUB.
2. Порядок глав, изображения, стили, ссылки и сноски сохраняются.
3. В изменённых XHTML-документах структура элементов и атрибутов совпадает с исходной, кроме явно разрешённых metadata-изменений; меняются текстовые узлы.
4. После импорта приложение автоматически извлекает словарь имён; исправленный пользователем вариант имени соблюдается в контрольных финальных сегментах.
5. Для каждого сегмента в итоговом EPUB существует отдельно сохранённый черновой перевод и успешно проверенный результат редактуры.
6. Кнопка «Остановить» во время перевода или редактуры переводит задачу в `paused`; «Продолжить» возобновляет нужный проход без новых запросов для готовых шагов.
7. Закрытие приложения после нескольких батчей и повторный запуск дают тот же результат восстановления.
8. `429`, timeout, пустой ответ DeepSeek и один некорректный JSON-ответ приводят к контролируемому retry, а не к потере задачи.
9. Постоянная ошибка переводит задачу в `needs_attention`; пользователь может повторить её после исправления настроек.
10. API-ключ отсутствует в `job.json`, логах, SSE и собранном frontend.
11. Битый и потенциально опасный EPUB отклоняется до запуска LLM-запросов.
12. Главный приёмочный прогон выполняется на паре English → Russian. Тот же пайплайн без изменения кода проходит дополнительную контрольную пару German → Polish; меняются только настройки задачи и содержимое prompt.

## 15. План реализации

### Этап 0 — технический spike

- Выбрать ZIP и XML/DOM библиотеки на двух реальных EPUB 2/3.
- Доказать round trip: распаковать и собрать книгу без перевода, открыть результат и проверить EPUBCheck при наличии.
- Доказать замену текстовых узлов без изменения DOM-структуры.

### Этап 1 — сквозной прототип

- DeepSeek Chat Completions через официальный OpenAI-compatible API.
- Импорт и разбор EPUB.
- Извлечение словаря имён и минимальный экран его проверки.
- Text-node extraction, batching, перевод и обязательная редактура, один LLM-запрос за раз.
- Сборка результата.
- Минимальный UI одной активной задачи с логом.

### Этап 2 — надёжный MVP

- Персистентные задачи и атомарные checkpoint-ы.
- «Остановить», «Продолжить», retry и recovery после перезапуска для обоих LLM-проходов.
- SSE, список глав и понятные ошибки.
- Жёсткая/мягкая валидация.
- Редактируемый словарь имён и инструкции.
- Автотесты на fixtures.

### Этап 3 — сравнение качества и удобство

- Просмотр оригинала и перевода по главам.
- Повтор выбранной главы.
- Статистика токенов и пользовательская оценка стоимости.
- Адаптер OpenAI и возможность назначить его на перевод, редактуру или оба прохода.
- Небольшой ручной A/B-набор фрагментов для сравнения DeepSeek и OpenAI до перевода целой книги.

### После MVP

- Генерация стилевого профиля.
- Профили персонажей, только если тесты покажут заметную пользу.
- Несколько провайдерских адаптеров.
- Управляемая параллельность запросов.
- Перевод nav/TOC и metadata.
- Упаковка в desktop-приложение, если запуск через терминал окажется неудобным.

## 16. Риски и способы снижения

| Риск | Последствие | Снижение |
|---|---|---|
| Модель пропускает или объединяет сегменты | Потеря текста | ID-контракт, schema validation, retry для обоих проходов |
| Редактор превращает перевод в пересказ | Потеря деталей оригинала | Оригинал в редакторском prompt, запрет сокращения, проверки ID и длины |
| Отправка HTML повреждает разметку | Невалидный EPUB | Перевод только text nodes, DOM reinsertion |
| Провайдер меняет лимиты/модель | Задача перестаёт запускаться | Настраиваемый профиль и test endpoint |
| Контекст/словарь имён не помещается | Обрезанный prompt | Token budget и релевантная выборка имён |
| Процесс закрывается | Потеря прогресса | Checkpoint после каждого батча |
| EPUB нестандартный | Ошибка разбора/сборки | Ранний preflight, fixtures, явное сообщение |
| Цена неизвестна заранее | Неожиданные расходы | Последовательный режим, usage stats, пользовательские тарифы |
| Локальный API доступен из сети | Утечка данных/ключа | Bind на `127.0.0.1`, без сетевого listen по умолчанию |

| Вопрос | Решение |
|---|---|
| Основной режим | Локальный single-user web app |
| Языки | По умолчанию EN → RU; выбираемая пара по BCP 47, минимум EN, RU, DE, PL |
| Backend | Node.js + TypeScript + Express |
| Frontend | React + Vite |
| Хранилище | Файлы на локальном диске, атомарные записи |

## 18. Открытые решения перед началом разработки

Эти вопросы не блокируют PRD, но должны быть закрыты на этапе 0:

1. Какая ОС является первым обязательным тестовым таргетом.
2. Какая актуальная модель DeepSeek используется для первого контрольного прогона; это настройка, а не константа в коде.
3. Переводить ли в MVP nav/TOC или оставлять исходные названия глав.
4. Нужен ли обязательный локальный EPUBCheck либо достаточно встроенной структурной проверки.
5. Где хранить API-ключ на первой ОС: только `.env` или системный keychain.
